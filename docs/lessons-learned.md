## 2026-10-06 lockfile を変える PR を 2 本続けてマージし、main の pnpm-lock.yaml が重複キーで壊れた

**概要**
#220（Prisma 7）のマージ直後に #213（eslint-plugin-jsdoc）をマージしたところ、main の `pnpm-lock.yaml` に同じキーが重複し、`pnpm install` が `ERR_PNPM_BROKEN_LOCKFILE` で失敗するようになった。どちらの PR も単体では CI が緑だった。

**詳細**:

- 何が起きたか: main（be11353）で `'@types/node@26.6.4':` のキーが正常時の 2 回から 4 回に増え、install が失敗した。main の CI と Vercel の本番デプロイが install の段階で落ちる状態になった。マージから約 10 分後、ローカルで `pnpm install` したときに気づいた。
- なぜ起きたか（根本原因）:
  - #213 は #220 より前の main を土台に CI が緑になっていた。マージ時、git は lockfile を YAML ではなくテキストとして 3-way マージするため、両者の変更が「衝突なし」として合成され、構造上ありえない重複キーができた。
  - マージ前にブランチを最新の main に追従させる必須設定がないため、**合成後の lockfile はどこでも検証されないまま main に入った**。
- 教訓 / 次からどうする:
  - **lockfile を変更する PR を続けてマージするときは、2 本目を最新の main に rebase（Dependabot なら `@dependabot rebase`）し、CI が通ってからマージする**。「両方とも緑」は「合成後も緑」を意味しない。
  - 壊れた lockfile は手で直さない。最後に正常だったコミットの lockfile を基準にし、後から載せる変更を `pnpm update <pkg>@<ver>` で載せ直す（PR で検証済みのバージョンに揃える）。
  - 恒久対策として、ruleset の「Require branches to be up to date before merging」を有効にするかを検討する（Dependabot の PR がマージのたびに rebase 待ちになるコストとのトレードオフ）。
- 関連: issue #222、PR #213、PR #220

## 2026-10-06 Dependabot が @prisma/client だけを major 更新し、CLI と食い違って CI が壊れた

**概要**
Dependabot PR #215 が `@prisma/client` を 7.10.0 に上げる一方、CLI の `prisma` は 6.19.3 のまま残した。CLI 6 が生成するクライアントを 7 のランタイムが読み込めず、CI が `Cannot find module …/query_engine_bg.postgresql.wasm-base64.js` で失敗した。

**詳細**:

- 何が起きたか: `@prisma/client` の major 更新 PR だけが作られ、`prisma` の PR は別に作られなかった（または揃わなかった）。CI の `lint-and-test` と Vercel のビルドが失敗した。本番への影響はない（マージ前に検出）。
- なぜ起きたか（根本原因）: `.github/dependabot.yml` は major を「1 依存 1 PR」で出す設定だった。Prisma は CLI とクライアントのバージョンが揃っていることが動作の前提だが、Dependabot はパッケージ間のその関係を知らないため、片方だけを上げる PR を作る。
- 教訓 / 次からどうする:
  - **バージョンを揃える必要がある依存の組（`prisma` / `@prisma/*` など）は、Dependabot の `groups` で major も含めて 1 つの PR にまとめる**。依存は最初に一致したグループに入るため、汎用の `minor-and-patch` より前に置く。
  - 依存更新の PR で「モジュールが見つからない」系のエラーが出たら、lockfile のパス（例: `@prisma+client@7.10.0_prisma@6.19.3`）から、組になるべきパッケージのバージョンの食い違いを先に疑う。
  - Prisma 7 は `.env` を暗黙に読み込まなくなった。2026-07-31 の本番データ全削除の原因になった経路そのものなので、`prisma.config.ts` に `import "dotenv/config"` を足して元に戻さない。
- 関連: issue #219、PR #215、`.github/dependabot.yml`、[`09-architecture-specification.md`](./09-architecture-specification.md)「Prisma 7 の構成と接続先の渡し方」

## 2026-10-04 必須チェックのワークフローに paths を付けていたため、docs のみの PR がマージ不能になった

**概要**
Dependabot 設定を追加する PR（#204）で、必須チェック `lint-and-test` が pending のまま完了せず、マージできなくなった。`ci.yml` にワークフローレベルの `paths`（`front/**`）があり、対象外の変更だけの PR ではワークフロー自体が起動しなかったため。

**詳細**:

- 何が起きたか: `.github/dependabot.yml` と `docs/` のみを変更した #204 が `BLOCKED` のままになった。同じ構造で `docs.yml`（必須チェック `Docs check`）も `paths` を持っており、front のみの PR では同様に詰まる状態だった。
- なぜ起きたか（根本原因）: 必須チェックは「チェックが報告されること」を待つ。ジョブの `if:` によるスキップは skipped として報告され成功扱いになるが、ワークフローレベルの `paths` で起動しなかった場合はチェック自体が存在せず、永久に pending になる。`.claude/rules/github-actions.md` に既知の課題として書かれていたが、ruleset で必須チェックに指定した時点で移行していなかった。
- 教訓 / 次からどうする: ruleset で必須チェックを追加するときは、そのワークフローに `on.*.paths` / `paths-ignore` が無いことを同時に確認する。あれば `paths-filter` + ジョブ `if:`、または（数十秒で終わるなら）常時実行へ移行してから必須にする。PR が `BLOCKED` で一部のチェックが表示すらされていないときは、まずワークフローの `paths` を疑う。
- 関連: issue #205、PR #204、[`.claude/rules/github-actions.md`](../.claude/rules/github-actions.md)「パスフィルタの実装（重要な落とし穴）」

## 2026-09-27 外部サービス必須のレートリミットを入れて本番デプロイが止まり、差し戻した

**概要**
Upstash Redis を使うレートリミット（PR #195）を、本番ビルドで環境変数を必須にする形で入れた。Upstash を用意しないままマージしたため本番デプロイが失敗し続け、本番は直前の版で止まった。さらに「本番デプロイは成功している」という確認を、別コミットのデプロイで誤認した。最終的に費用対効果を見直して差し戻した（#196）。

**詳細**:

- 何が起きたか: #195 のマージ後、本番ビルドが `[rate-limit] 本番ビルドには UPSTASH_REDIS_REST_URL と ... が必要です` で失敗した。Vercel は直前の READY（#194）を配信し続けたため、サイトは正常に見えていた。本番に 22 回リクエストしても 429 が返らないことで発覚した。
- なぜ起きたか（根本原因）:
  - 設計時に「実装として正しいか」だけを評価し、**外部サービスを誰がいつ用意するか（運用コスト）と、それに見合う脅威か**を評価していなかった。issue に書かれた手段（Upstash の移植）を前提として受け取り、手段そのものを問い直さなかった。
  - デプロイ成功の確認で、**一覧の READY がどのコミットのものかを照合しなかった**。失敗したデプロイの直前の READY を「今回のデプロイ」と取り違えた。
- 教訓 / 次からどうする:
  - 外部サービス・シークレット・アカウントが増える設計は、実装前に「その脅威の大きさ」と「運用コスト（用意する人・タイミング・費用）」を並べて提示し、導入の是非から合意する。issue に手段が書かれていても、手段の妥当性は別に確認する。
  - 本番の外部設定を前提にする変更は、**その設定が済んでからマージする**。PR 本文に書くだけでなく、マージ前にユーザーへ明示的に確認する。
  - 本番反映の確認は、**本番で動いているデプロイのコミット SHA がマージしたコミットと一致するか**で判断する（`vercel.md` の「古いものが正常に見えている」失敗と同じ構造）。
- 関連: issue #193 / #196、PR #195、`docs/06-security-specification.md`「レートリミット（不採用）」、`.claude/rules/vercel.md`

## 2026-09-26 Next.js 16.3 への更新で dev サーバーが 127.0.0.1 からの開発用リソースを遮断し E2E が全滅した

**概要**
脆弱性対応で Next.js を 16.1.4 → 16.3.6 に上げたところ、unit / IT / build はすべて通るのに E2E だけ 27 件中 25 件が失敗した。原因は DB でもテストでもなく、dev サーバーの cross-origin 遮断が既定で有効になったことだった。

**詳細**:

- 何が起きたか: E2E の各テストがタイムアウト。ページのスナップショットでは一覧が空・管理者セッションも未反映で、エラーバナーも出ていなかった。`page.route()` でモックしている管理者テストまで落ちていた。
- なぜ起きたか（根本原因）: Next.js 16.3 の dev サーバーは、自身が認識するオリジン（`localhost`）と異なるオリジンからの開発用リソース（`/_next/hmr` 等）を既定で遮断する。Playwright の baseURL は `http://127.0.0.1:3100` のため cross-origin 扱いとなり、クライアント側の処理（一覧取得・セッション判定）が動かなかった。dev サーバーを手で起動すると `Blocked cross-origin request to Next.js dev resource /_next/hmr from "127.0.0.1"` がログに出ており、これで特定できた。
- 教訓 / 次からどうする:
  - **「モックを使うテストまで落ちている」なら、DB ではなくクライアント JS が動いていないことを疑う。** 切り分けとして、同じ dev サーバーを手で起動し、ブラウザのコンソールと dev サーバーのログを直接見る。
  - フレームワークのマイナー更新でも、E2E（dev サーバー経由）は unit / IT / build が通っても壊れうる。依存更新の PR では E2E まで必ず回す。
  - 対処は `front/next.config.ts` の `allowedDevOrigins: ["127.0.0.1"]`（dev 専用・本番に影響なし）。
- 関連: issue #191、`docs/08-test-specification.md`（E2E の前提）、`.claude/rules/testing.md`（「テストが全滅したら、まず接続先を疑う」— 今回は接続先の確認で DB を除外した上で、次の層を疑った）
