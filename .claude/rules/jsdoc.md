# JSDoc 規約（TypeScript）

正準は [`docs/10-miscellaneous-specification.md`](../../docs/10-miscellaneous-specification.md) の「コメント・JSDoc 方針」。本ファイルはその要約。

## 基本方針

**関数・カスタムフック・コンポーネントには原則すべて、先頭に 1 行（必要なら数行）の意図コメントを付ける。** 後から読み返したときに「本文を追わなくても何をするか分かる」状態を優先する。内部のヘルパー関数・`useCallback` / `useEffect` も対象（効果には `//` 行コメントでも可）。

一貫して付けることで「これは書くべきか？」の判断コストをなくし、どの関数にも先頭に説明がある均一な読み心地を保つ。

## 必須対象（公開シンボル）

- `export` された関数・型（`type` / `interface`）・定数
- **型のメンバー**（各プロパティ、union リテラルの各値）— 次節参照
- コンポーネントの **props 型**（各プロパティ）
- カスタムフック（`useXxx`）と、**その戻り値の各メンバー**
- Route Handler・`lib/` の公開関数

**任意対象**: `export` されない内部関数、コンポーネント内に閉じた `useState`・ハンドラ、自明な 1 行ユーティリティ。ただし意図が非自明なものは内部でも付ける。

## 型定義のコメント（型本体 + メンバー）

`type` は**型本体と各メンバーの両方**に付ける。型シグネチャは「形」しか語らず、**意味・単位・制約**はコメントでしか残せない。

- **型本体**: 「何を表す型か」＋どの層のものか（API レスポンス / 画面用モデル / props）。
- **各プロパティ**: 型名から読めない情報。特に**単位**、**`null` / 省略の意味**（「未設定」か「該当なし」か）、**制約・不変条件**は必須。自明なもの（`id` 等）は省略してよく、**埋め草コメントを付けない**。
- **union リテラル**: 各値がどの状態を指すかを個別に書く。
- **Zod 由来の型（`z.infer`）**: 実体はスキーマ側にあるため、**コメントもスキーマ（`lib/schemas/`）のフィールドに書く**。`z.infer` エイリアスには型本体の説明のみ（両方に書くと二重管理）。

例は正準 [`docs/10-miscellaneous-specification.md`](../../docs/10-miscellaneous-specification.md) を参照。

## 記述ルール（TypeScript strict 前提 / TSDoc スタイル）

- **型は書かない**: 型は TypeScript のシグネチャが唯一の真実。JSDoc に `{string}` 等の型ブレースは書かない（二重管理・型ずれの原因）。
- **全引数を `@param` で説明**: JSDoc ブロックを持つ関数は全引数に `@param 名 説明` を付ける（型は書かず「何を表す値か / 非自明な制約」を書く）。分割代入 props は型（`XxxProps`）が真実なので `props.x` 単位に展開しない。
- **`@returns` で返り値を説明**: `.ts` のフック / lib / API は `@returns` に返り値の意味を書く。React コンポーネント（`.tsx`）は不要（「@returns …の要素」はノイズ）。
- **`@throws` で例外を説明**: 意図的に例外を投げる場合、どの条件で throw するかを書く。**型ブレース（`@throws {Error}`）は書かない**。呼び出し側は throw の有無をシグネチャから知れないため、コメントが唯一の手掛かりになる。
- **「何を / なぜ」を簡潔に**: 実装の逐次翻訳ではなく、役割・非自明な契約・分岐理由・副作用を書く。
  - 例: 認可の 401/403 の切り分け理由、フォールバック値の理由、正規表現の対応形式、遅延実行・再取得のタイミング。
- **フック / コンポーネントは「まとまりとしての役割」**: 何の状態機械か、返り値・表示の責務を書く。
- **記法**: 日本語。`/** */`（複数行や公開 API）と `//`（短い補足・効果）を使い分ける。
- 自明な 1 行 setter も一貫性のため短く付けてよいが、冗長・実装追認のコメントは避ける。

## 状態・ロジック層のコメント（カスタムフック）

カスタムフックの戻り値は**定義ファイルを開かずに使われる**ため、値の意味・関数の効果はコメントでしか伝わらない。

- **必須ラインは「参照範囲」で決める**（[`typescript.md`](./typescript.md)「型定義の配置」と同じ軸）。
  - **ファイルを越えて使われる**（フック戻り値の各メンバー、Context value、`export` された関数・定数）→ **必須**
  - **ファイル内に閉じる**（コンポーネント内の `useState`・ハンドラ）→ **条件付き**（「なぜ」が非自明なときのみ）
  - コンポーネント内部まで一律必須にしない。`setIsOpen` に「isOpen をセットする」のような**埋め草で重要なコメントが埋もれる**ため。
- **戻り値型を明示し、コメントは型のメンバーに書く**。推論任せだと返すオブジェクトの中身は「宣言」ではなく「式」になり、JSDoc も lint も届かない。明示すれば型メンバーのコメント規約がそのまま効く。
  - 既存フックの多くは推論任せのため、**新規・改修時に明示へ寄せる**（一括の型付けはしない）。
- **書く内容はシグネチャから読めない情報に限る**: いつ / 誰が変えるか、初期値・空値の意味（「空配列は『0 件』であり『未取得』ではない」）、副作用の有無、他の値との不変条件。

## 混乱テスト（公開/内部・本番/テストを問わない）

判断軸は「public か否か」ではなく、**「1 か月後の自分／他プロジェクトから戻ってきた読み手が『これは何？なぜ？』となるか」**。なるなら、`export` されていない内部関数でもテストコードでも "why" を残す。

- **キャスト・回避策には "why" 必須**: `as unknown as` / `as any` / `@ts-ignore` / `@ts-expect-error` / マジック値 / 複雑な正規表現 / 明示的なワークアラウンドは、**型を欺く・仕様を迂回する根拠がコードから消える**ため、コメントが唯一の記録になる。
- **テスト足場も対象**: SUT ビルダー・複雑な fixture・非自明な mock は、意図が読み取りにくいなら付ける。

## Lint による強制

機械的に判定できる違反（JSDoc への型の再掲など）のみ lint で強制する。**有効ルール・重大度の唯一の真実は [`front/eslint.config.mjs`](../../front/eslint.config.mjs)**、採用/不採用の根拠は正準 [`docs/10-miscellaneous-specification.md`](../../docs/10-miscellaneous-specification.md) を参照（要約側でルール一覧を持たず、drift を避ける）。**コメントの有無・質はレビューで確認する。**

強制の考え方は以下のとおり。

- **型定義のコメントは `src/types/**` に限って機械強制する**（型本体・型メンバー）。`src/**` 全体に広げると関数シグネチャ内のインラインオブジェクト型を誤検知し、「埋め草コメントを付けない」方針と衝突する。
- **関数への `require-jsdoc` は採用しない**（許容している `//` 行コメントを誤検知するため）。レビューで担保する。
- **オブジェクトリテラルのプロパティを直接 Lint で強制しない**（宣言ではなく式のため実効性が低い）。フックの戻り値・Context value は**型を先に定義する**ことで同じルールに乗せる — これが「型へ寄せる」方針の要。
